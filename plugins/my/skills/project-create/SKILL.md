# 프로젝트 생성

- 스택을 가장 먼저 확정한다. 스택이 정해지기 전에는 파일을 만들지 않는다.
- 뼈대는 공식 생성기로 만들고, 그 위에 템플릿(`project.mjs scaffold`)을 덮는다. 템플릿에는 버전이 없다. 버전은 이번 생성 때 확인해 `docs/stack.md`에 적는다.
- 생성기·의존성 설치는 패키지를 내려받으므로 명령, 만들 폴더, 확인한 버전을 보여 주고 승인받은 뒤 실행한다.
- 이미 있는 파일은 덮어쓰지 않는다.

스크립트: 이 스킬 폴더 기준 `../../scripts/project.mjs`를 Node로 실행한다. 프로젝트 루트는 실행한 폴더의 git 루트(없으면 그 폴더)로 정해지므로, 프로젝트 폴더에서 스크립트의 절대 경로로 실행한다. 스킬 폴더로 이동해 실행하지 않는다.

## 할 일

1. **프로젝트 폴더**: `{name}`(영문 kebab-case)을 확인한다. 없거나 형식이 다르면 제안해 확인받는다. "현재 폴더에 만들기 / 하위 폴더 `{name}/`을 만들고 거기서 진행"을 묻는다. 현재 폴더에 파일이 있으면 목록 요약을 함께 보여 준다.
   - 스크립트는 git 루트를 프로젝트 루트로 쓴다. 고른 폴더가 자기 git 저장소의 루트가 아니면(git 저장소가 아니거나 상위 폴더의 저장소 안이면) 그 폴더에서 `git init`을 하자고 묻고 승인받은 뒤 한다. 이후 명령은 모두 그 폴더에서 실행한다.
2. **스택 확정**: `project.mjs stacks`로 쓸 수 있는 스택을 보여 준다. 무엇을 만들지 듣고 스택, 역할(스택이 둘 이상이면 `apps/<역할>/`), DB, 계약 형식(OpenAPI 등)을 제안해 확인받는다.
   - 목록에 없는 스택이면 템플릿이 아직 없다고 알리고 멈춘다. `마이 플러그인 문제 {내용}`으로 스택 추가를 기록하라고 안내한다.
   - 스프링이면 패키지 이름(`com.example.app` 형식)을 확인받는다.
3. **버전 확인**: 쓸 도구·프레임워크의 현재 버전을 context7이나 공식 레지스트리(`npm view`, PyPI, Maven Central 등)에서 확인한다. 확인하지 못한 것은 "미확인"으로 둔다. context7을 쓰지 못했으면 "context7 미사용"을 적고 설치·인증은 `마이 플러그인 현황`의 권장 플러그인 안내를 따르라고 한 줄 덧붙인다.
4. **계획 보여 주기**: 아래를 한 번에 보여 주고 "진행 / 고치기 / 취소"를 묻는다.
   - 스택별 공식 생성기 명령과 실행 위치. 명령은 템플릿 `stack.part.md`의 "생성 도구"를 기준으로 하되 공식 문서로 다시 확인한다.
   - 확인한 버전 표.
   - `project.mjs scaffold <스택[:역할]>... --name {name} [--var package=<패키지>] [--gemini] --plan` 출력(만들 파일, 이미 있어 건너뛸 파일). Gemini CLI·Antigravity CLI를 쓰면 `--gemini`를 붙인다.
5. **생성기 실행**: 승인하면 스택 폴더가 비어 있을 때만 공식 생성기를 실행한다. 비어 있지 않으면 실행하지 말고 "생성기 건너뜀 / 취소"를 묻는다. 생성기가 묻는 항목은 계획대로 답하고, 계획에 없는 질문이 나오면 멈추고 묻는다.
6. **템플릿 덮기**: `project.mjs scaffold ... --plan`을 다시 실행해 생성기가 만든 파일과 겹치는 것을 보여 준다. 겹치는 파일이 있으면 "겹치는 파일은 그대로 두고 나머지만 / 취소"를 묻고, 고르면 `--skip-existing`으로 실행한다. 겹치지 않으면 그대로 실행한다.
   - 건너뛴 설정 파일(예: 생성기가 만든 lint 설정)은 템플릿 쪽 설정과 무엇이 다른지 요약하고, 합칠지는 사용자가 정한다.
7. **스택 추가 설정**: `docs/stack.md`의 스택 절에 "더할 것"(예: 스프링의 `build.gradle.kts` 플러그인)이 있으면 바꿀 내용을 diff로 보여 주고 승인받은 뒤 고친다. 버전은 3단계에서 확인한 것을 쓴다.
8. **stack.md 채우기**: `docs/stack.md`의 버전 표에 3단계에서 확인한 버전과 근거(레지스트리·문서)를 적고, 경계별 원본과 DB를 채운다. 확인하지 못한 칸은 "미확인"으로 둔다. 스택별 명령 표는 고치지 않고, 생성기 결과와 다르면 다른 점을 사용자에게 알리고 승인받은 것만 고친다.
9. **설치·점검**: 의존성 설치 명령을 보여 주고 승인받은 뒤 실행한다. lock 파일(`uv.lock`, `pnpm-lock.yaml` 등)이 생겼는지 확인하고, 없으면 무엇을 실행하면 생기는지 알린다. Gradle은 의존성 잠금을 따로 켜지 않으면 lock 파일이 없으므로 "lock 없음"으로 적는다. `docs/stack.md` 명령 표의 lint·타입 검사·테스트를 실행해 결과를 보여 준다. 마지막으로 `project.mjs check`를 실행한다.
10. **다음 단계**: `마이 프로젝트 {name} 정의`를 안내한다.

질문은 선택지 질문 도구가 있으면 그것으로 묻고, 없으면 번호 목록으로 묻고 번호로 답을 받는다.

## 멈출 때

- `project.mjs`가 "프로젝트 오류"로 끝나면 메시지를 보여 주고 멈춘다. 템플릿 파일을 손으로 복사해 대신하지 않는다.
- 생성기나 설치가 실패하면 출력을 보여 주고 "다시 시도 / 그 단계 건너뜀 / 멈춤"을 묻는다. 실패를 감추고 다음 단계로 가지 않는다.
- 비대화형 실행이면 1~4단계의 계획만 보여 주고 "승인 대기 — 대화형에서 다시 실행"을 적는다. 폴더·파일을 만들거나 생성기·설치를 실행하지 않는다.

## 결과

- 끝: 프로젝트 루트, 스택과 위치, 확인한 버전(미확인 표시 포함), 실행한 생성기·설치 명령, 만든 파일 수와 건너뛴 파일, lint·타입 검사·테스트·`check` 결과, 다음 단계.

## 하지 말 것

- 템플릿이나 `docs/stack.md`에 기억에 의존한 버전을 적지 않는다.
- 사용자 승인 없이 기존 파일을 지우거나 덮어쓰지 않는다.
