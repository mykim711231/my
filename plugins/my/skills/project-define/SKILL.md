# 프로젝트 정의

- 계약(DB·API·공용 타입)을 구현보다 먼저 정한다. DB 쪽과 화면 쪽이 중간 계약을 각자 추측해 만들면 서로 어긋난다.
- 명세는 기능 하나에 파일 하나다. 절은 목표 / 범위 밖 / 요구사항 / 수용 기준 / 기술 계획 / 작업 / 검증 결과 일곱 개를 그대로 쓴다.
- 요구사항은 EARS 형식("~할 때 시스템은 ~한다")으로 쓰고 ID(`REQ-01`)를 붙인다. 수용 기준은 테스트로 확인할 수 있게 쓴다.
- 이 단계는 문서와 계약 파일만 만든다. 구현 코드는 쓰지 않는다.

스크립트: 이 스킬 폴더 기준 `../../scripts/project.mjs`를 Node로 실행한다. 프로젝트 루트는 실행한 폴더의 git 루트로 정해지므로, 사용자의 원래 작업 폴더에서 스크립트의 절대 경로로 실행한다. 스킬 폴더로 이동해 실행하지 않는다.

## 할 일

1. **읽기**: `AGENTS.md`, `docs/stack.md`(경계별 원본, 계약 형식), `docs/requirements.md`, 기존 명세, `contracts/`, `db/migrations/`를 읽는다. `docs/stack.md`가 없으면 `마이 프로젝트 {name} 생성`을 먼저 하라고 안내하고 멈춘다.
2. **범위 정하기**: 이번에 정할 기능을 듣는다. 작은 작업(파일 몇 개, 계약 변경 없음)이면 명세 없이 `마이 프로젝트 {name} 구현`으로 바로 가도 된다고 알리고 고르게 한다.
3. **요구사항**: 기능을 요구사항으로 나눠 다음 ID부터 번호를 붙인 초안을 보여 준다. 기존 ID와 겹치거나 기존 요구사항을 바꾸는 것이면 따로 표시한다. 확인받으면 `docs/requirements.md` 표에 상태 `초안`으로 더하고 `updated`를 오늘 날짜로 바꾼다.
4. **명세 만들기**: 명세 이름(영문 kebab-case)과 제목을 제안해 확인받는다. `project.mjs new-spec <이름> --title <제목>`으로 만들고, 출력된 파일의 앞머리 `reqs`에 이번 요구사항 ID를 적은 뒤 일곱 절을 채운다. 앞머리 `status`는 `draft`로 둔다.
5. **계약 초안**: `docs/stack.md`의 경계별 원본에 맞춰 초안을 만든다. 원본이 코드인 경계(예: FastAPI 모델 → OpenAPI)는 원본 파일의 모델·엔드포인트 시그니처까지만 쓰고, 생성물은 손으로 만들지 않는다.
   - DB: 마이그레이션 초안(`db/migrations/`). 테이블·열 주석에 요구사항 ID를 남긴다.
   - API·공용 타입: `contracts/` 또는 원본 코드. 경로·이름·필수 여부·오류 응답을 정한다.
   - 화면: 화면 목록과 각 화면이 쓰는 데이터 필드를 명세의 기술 계획 절에 표로 적는다. 필드는 API 스키마 이름과 같게 쓴다.
   - 첫 기능이면 기술 계획에 "기준 구현"이라고 적는다.
6. **점검**: `project.mjs check`를 실행한다. 이번에 만든 파일의 문제는 고치고 다시 점검한다. 다른 파일의 문제는 보고만 한다.
7. **사람 승인**: 요구사항, 명세 요약, 계약 초안을 보여 주고 "승인 / 고치기 / 보류"를 묻는다. 승인하면 명세 `status`를 `approved`, 해당 요구사항 상태를 `승인`으로 바꾸고, 명세 작업 절의 `계약 확정`을 체크한다. 명세와 `docs/requirements.md` 둘 다 `updated`를 오늘 날짜로 바꾼 뒤 `project.mjs check`를 다시 실행한다.
8. **다음 단계**: `마이 프로젝트 {name} 구현`을 안내한다.

질문은 선택지 질문 도구가 있으면 그것으로 묻고, 없으면 번호 목록으로 묻고 번호로 답을 받는다.

## 멈출 때

- `project.mjs`가 "프로젝트 오류"로 끝나면 메시지를 보여 주고 멈춘다. 명세 파일을 직접 만들지 않는다.
- 요구사항이 모호해 수용 기준을 테스트로 쓸 수 없으면 질문 목록을 보여 주고 답을 받기 전에는 명세를 승인 상태로 바꾸지 않는다.
- 비대화형 실행이면 요구사항·명세·계약 초안을 출력만 하고 "승인 대기 — 대화형에서 다시 실행"을 적는다. 파일을 쓰지 않는다.

## 결과

- 끝: 더한 요구사항 ID, 명세 파일과 상태, 만든 계약 파일, `check` 결과, 승인 여부, 다음 단계.

## 하지 말 것

- 사람 승인 없이 `status: approved`나 요구사항 `승인`을 적지 않는다.
- 이미 승인된 명세의 요구사항·계약을 말없이 바꾸지 않는다. 바꿀 때는 무엇이 달라지는지 보여 주고 다시 승인받는다.
