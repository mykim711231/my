# 프로젝트 구현

- 계약이 확정된 뒤 시작한다. 구현할 명세는 `status: approved`인 것만이다. 작은 작업(계약 변경 없음)은 명세 없이 해도 되지만 범위를 먼저 확인받는다.
- 수직 슬라이스로 만든다. 기능 하나를 DB → 서버 → 계약 생성 → 화면 → 테스트까지 끝내고 동작을 확인한 뒤 다음 기능으로 간다. 계층별로 전체를 먼저 만들지 않는다.
- 경계마다 원본은 하나다. `docs/stack.md`의 경계별 원본을 고치고 나머지는 명령 표의 생성 명령으로 다시 만든다. 생성된 파일은 손으로 고치지 않는다.
- 요구사항 ID를 스키마 주석, API(설명·태그), 화면, 테스트 이름에 남긴다.

스크립트: 이 스킬 폴더 기준 `../../scripts/project.mjs`를 Node로 실행한다. 프로젝트 루트는 실행한 폴더의 git 루트로 정해지므로, 사용자의 원래 작업 폴더에서 스크립트의 절대 경로로 실행한다. 스킬 폴더로 이동해 실행하지 않는다.

## 할 일

1. **고르기**: `docs/specs/`에서 `status: approved`인 명세를 보여 주고 이번에 구현할 것을 고르게 한다. 없으면 `마이 프로젝트 {name} 정의`를 안내하고 멈춘다.
2. **먼저 읽기**: 작업마다 아래를 읽고, 읽은 파일 목록을 한 줄로 보여 준다.
   - `AGENTS.md`, `docs/stack.md`(버전, 경계별 원본, 명령 표), 고른 명세, 명세의 `reqs`에 걸린 계약 파일(`contracts/`, `db/migrations/`, 원본 코드).
   - 기준 구현: 명세 기술 계획에 "기준 구현"이라고 적힌 첫 기능의 코드. 이번 기능이 기준 구현이면 템플릿 `sample/`의 계약 테스트를 출발점으로 삼는다.
   - 기술 규칙: `docs/stack.md`와 의존성 파일(`pyproject.toml`, `package.json`, `build.gradle.kts` 등)로 쓰는 기술을 식별한다. 기술별 규칙 참고 파일이 있으면 읽는다. 읽지 못했으면 그 기술의 규칙 적용 상태를 "미확인"으로 둔다.
   - API·문법·버전 사실은 context7에서 의존성 파일의 버전에 맞춰 가져온다. 실패하면 공식 문서를 보고 결과에 "context7 미사용"을 적는다. 기억으로 쓰지 않는다.
3. **계획**: 명세의 작업 절을 기능 단위 순서로 보여 준다. 각 작업에 바꿀 원본 파일, 다시 생성할 파일, 남길 요구사항 ID, 확인할 테스트를 붙인다. 계약을 바꿔야 하는 작업이 있으면 따로 표시하고 "명세로 돌아가 다시 승인 / 계약 변경 없이 진행 방법 찾기"를 묻는다.
4. **구현**: 작업을 하나씩 한다.
   - 원본을 고치고 `docs/stack.md` 명령 표의 생성 명령을 실행한다. 생성 뒤 타입 검사가 실패한 곳을 모두 고친다. 계약을 우회해 한쪽만 고치지 않는다.
   - 기준 구현의 구조·이름·오류 처리 패턴을 따른다. 다르게 해야 하면 이유를 적고 확인받는다.
   - 의존성을 새로 더해야 하면 이름, 버전(확인한 근거), 이유를 보여 주고 승인받은 뒤 설치하고 `docs/stack.md`에 적는다.
   - 수용 기준마다 테스트를 쓴다. 모듈 경계마다 계약 테스트가 하나 이상 있게 한다.
5. **기능 끝 확인**: 기능 하나가 끝나면 명령 표의 lint·타입 검사·테스트와 생성 명령의 차이 검사를 실행한다. 실패하면 고치고 다시 실행한다. 통과하면 명세의 작업 절에서 끝낸 작업을 체크한다.
6. **추적표**: `project.mjs trace`로 `docs/trace.md`를 다시 만들고, 이번 요구사항 ID의 빈칸(—)을 보여 준다. 그다음 `project.mjs check`를 실행한다.
7. **다음 단계**: 남은 작업이 있으면 다음 기능을 묻는다. 모두 끝났으면 `마이 프로젝트 {name} 검증`을 안내한다. 작업을 멈출 때는 `마이 작업 종료`로 인계 문서를 남기라고 안내한다.

질문은 선택지 질문 도구가 있으면 그것으로 묻고, 없으면 번호 목록으로 묻고 번호로 답을 받는다.

채팅 모드(셸·파일 도구가 없거나 이 스킬 폴더 기준 `../../scripts`가 없음)면 이 본문 대신 같은 폴더의 `chat.md`를 따른다. 스크립트가 실행됐다가 실패한 것은 채팅 모드가 아니다.

## 멈출 때

- 명세나 계약과 맞지 않는 요구가 나오면 구현을 멈추고 무엇이 다른지 보여 준 뒤 `마이 프로젝트 {name} 정의`로 고칠지 묻는다.
- 같은 검사가 세 번 고쳐도 실패하면 멈추고 실패 출력, 시도한 것, 추정 원인을 보여 준다.
- `project.mjs`가 "프로젝트 오류"로 끝나면 메시지를 보여 주고 멈춘다. `docs/trace.md`를 손으로 쓰지 않는다.
- 비대화형 실행이면 2~3단계(읽은 파일, 계획)만 보여 주고 "승인 대기 — 대화형에서 다시 실행"을 적는다.

## 결과

- 끝: 구현한 명세와 작업, 바꾼 원본 파일과 다시 생성한 파일, 남긴 요구사항 ID, 검사 결과(명령과 통과·실패), 추적표 빈칸, 기술 규칙 적용 상태(읽은 참고 파일 / 미확인), context7 사용 여부, 다음 단계.

## 하지 말 것

- 생성된 파일을 손으로 고치지 않는다.
- 승인되지 않은 명세를 구현하지 않는다. 명세의 `status`를 바꾸지 않는다(완료 승인은 검증 단계에서 한다).
- 실패한 테스트를 지우거나 건너뛰게 바꿔 통과시키지 않는다.
